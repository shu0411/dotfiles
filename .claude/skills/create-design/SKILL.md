# create-design — 設計ドキュメントの作成・更新

`docs/concept.md`（人間が書いたアイデア・要求のメモ）を入力として、実装を開始できる
粒度の `docs/design.md` を作成・更新する。対象は主に個人開発の小規模プロジェクト。

ドキュメントは次の 2 ファイルだけで運用し、ファイルを増やさない。

```text
docs/
├── concept.md   ← 人間が書く。曖昧さを許容する軽量なアイデアメモ
└── design.md    ← このスキルが作る。仕様設計と技術設計を章で分けた 1 ファイル
```

このスキルの責務は設計ドキュメントの作成・更新まで。**実装コード・テストコードの
作成、パッケージのインストール、コード修正は行わない。** 実装は `design.md` が
`Ready for Implementation` になった後、別の指示で行う。

## 最重要原則 1: 仕様と実装方法を同時に考えない

必ず次の順序で進める。

```text
concept.md
    ↓
仕様設計を作成
    ↓
人間が仕様を確認・確定
    ↓
技術設計を作成
    ↓
人間が技術設計を確認
    ↓
実装開始
```

**仕様設計が確定する前に技術設計を作成してはならない。** 技術的に実装しやすい形から
逆算して仕様を決めてしまい、本来作りたかったものとずれた状態で実装まで進むことを
防ぐためである。

## 最重要原則 2: ファイル内の SSOT を守る

仕様設計・技術設計に共通するルールとして、**同じ内容を design.md 内の複数箇所に
繰り返して記載しない**。各情報の記載場所を 1 か所に定め、他の箇所からは章番号や
リンクによる参照で示す。

- 複数の機能に共通する振る舞いは「1.6 機能間の共通ルール」に一度だけ書き、
  各機能仕様（1.5）では繰り返さず参照する
- 技術設計では、仕様設計に書かれた内容（受け入れ条件、入出力の定義など）を
  再掲しない。「1.5 の受け入れ条件に対応」のように参照する
- 背景・目的は concept.md から長文でコピーせず、必要なら参照で示す
- 同じデータ構造・同じルールを 2 か所以上に書きそうになったら、定義場所を
  1 つに決めて他を参照に置き換える

重複した記述は更新漏れによる矛盾の温床になり、小規模開発ではその矛盾を検知する
仕組みがないため、記載時点で防ぐ。

## 実行手順

### Step 1: 入力の確認と状態判定

1. `docs/concept.md` を読む。**存在しなければ停止**し、ユーザーに concept.md の
   作成を促す（勝手に代筆しない）
2. プロジェクトの `AGENTS.md` / `CLAUDE.md` があれば読み、既存ルールに従う
3. 既存コード・README・テストがあれば、関係する部分だけ確認する
4. `docs/design.md` の有無と、冒頭の `Status:` の値から動作モードを決める

| design.md の状態 | モード |
| --- | --- |
| 存在しない | A: 仕様設計の新規作成 |
| `Functional Specification Draft` | B: 仕様設計の更新・確定確認 |
| `Functional Specification Confirmed` | C: 技術設計の作成 |
| `Technical Design Draft` | D: 技術設計の更新・確定確認 |
| `Ready for Implementation` | E: 実装可能 |

**例外:** 仕様確定後（モード C〜E）に `concept.md` または design.md の仕様設計の章に
変更が入っていた場合は、モードに関わらず「仕様変更フロー」（後述）に従う。

### モード A: 仕様設計の新規作成

1. [template.md](template.md) の章立てに従って `docs/design.md` を新規作成する
2. **「1. 仕様設計」の章のみ記載する。技術設計の章は作成しない**
3. `Status: Functional Specification Draft` とする
4. 合理的に補った仮定は本文中に「仮定:」として明示し、決められないものは
   「1.7 未決事項」に整理する（「曖昧な要求の扱い」参照）
5. 最後に、重要な仮定と未決事項を要約して提示し、ユーザーに仕様設計の確認を求める

### モード B: 仕様設計の更新・確定確認

- 修正依頼があれば **仕様設計の章のみ** 更新する。技術設計は引き続き作成しない
- ユーザーが **明示的に** 仕様を確定した場合（例:「仕様を確定して」「これで OK、
  技術設計に進んで」）のみ、`Status: Functional Specification Confirmed` に変更する
- **ユーザーの沈黙や、単なる技術的な質問を仕様確定とみなさない。** 確定の意思が
  読み取れない場合は、確定してよいかを質問する
- 同じ会話の中で確定されたら、続けてモード C に進んでよい

### モード C: 技術設計の作成

1. 確定済みの仕様設計を読む
2. リポジトリの既存構成、コード、テスト、依存ライブラリを確認する
3. 既存の設計・命名規則に合わせて「2. 技術設計」の章を作成する
4. テスト方針は仕様設計の **受け入れ条件と 1 対 1 で対応** させ、TDD で先に書く
   テストを明示する
5. 実装順序を整理する
6. `Status: Technical Design Draft` に変更する
7. 技術的リスクと未決事項を要約して提示し、ユーザーに技術設計の確認を求める

途中で仕様の問題（矛盾、不足、実現困難な要求、パフォーマンス上の問題、既存構成との
重大な衝突）が見つかった場合は「仕様変更フロー」に従い、**独断で仕様を変更しない**。

### モード D: 技術設計の更新・確定確認

- 修正依頼があれば技術設計の章のみ更新する。**確定済みの仕様は変更しない**
- ユーザーが明示的に問題なしとした場合のみ、`Status: Ready for Implementation` に
  変更し、実装を開始できる状態になったことを伝える

### モード E: 実装可能

- 変更がなければ、design.md は実装可能な状態であることを伝えて終了する
  （実装自体はこのスキルでは行わない）

## 仕様変更フロー

仕様確定後に concept.md や仕様設計が変更された場合、および技術設計中に仕様の問題が
見つかった場合は、**技術設計をそのまま更新してはならない**。次の順序で扱う。

1. `Status: Functional Specification Draft` に戻す
2. 仕様設計を更新する（技術設計中に見つかった問題は、仕様へのフィードバックとして
   明示する）
3. 既存の技術設計への影響を「2.7 技術的リスク・未決事項」等に明示する
   （技術設計の本文は更新しない）
4. そこで停止し、ユーザーに仕様の再確認を求める
5. 仕様が再確定した後、モード C として技術設計を更新する

## 仕様設計で扱う内容

利用者や外部から見た振る舞いを定義する。対象範囲・対象外、想定ユーザー、利用場面、
機能一覧、操作フロー、入力、出力、状態変化、制約、バリデーション、エラー時の挙動、
空状態の挙動、完了条件、受け入れ条件、機能間で共通するルール、未決事項。

**受け入れ条件は、後からテストへ変換できる具体的な表現にする。**
「〜のとき、〜すると、〜になる」の形で、条件・操作・結果が観測可能なように書く。

### 仕様設計で決めてはいけない内容

コンポーネント名、クラス名、関数名、モジュール構成、ファイル・ディレクトリ構成、
状態管理ライブラリ、ストア構造、データベースの物理設計、API エンドポイント、
内部アルゴリズム、実装順序、テストライブラリ、配置・デプロイ構成。

技術スタックが concept.md で決まっている場合は制約として参照してよいが、
**技術的な都合で仕様を変更してはならない**。

## 技術設計で扱う内容

確定済みの仕様をどのように実現するかを定義する。現在のリポジトリ構成、システム構成、
責務の分離、コンポーネント・モジュール構成、状態管理、データ構造、データフロー、
永続化方法、インターフェース、エラー処理方式、使用する既存ライブラリ、新規依存
ライブラリの必要性、テスト方針、TDD で先に作るテスト、実装順序、技術的リスク。

### 技術設計で守ること

- 確定済みの仕様を変更しない
- 技術的に実装しやすいという理由で、利用者から見える挙動を変えない
- YAGNI を守り、対象外機能を見越した抽象化をしない
- 既存コードの構成、命名、依存関係を優先する
- 新しい依存ライブラリは必要性が明確な場合だけ追加する
- 私的な関数や細かなコード構造まで過剰に決めない。実装コードの疑似的な複製となる
  ほど詳細に書かず、**責務と境界がレビューできる粒度** にとどめる
- テスト方針は仕様設計の受け入れ条件と対応させる

## 曖昧な要求の扱い

不足情報をすべて質問すると作業が止まるため、**質問は最小限にする**。

### 合理的に補ってよいもの（重要な仮定は本文に明示する）

- 明示された制約から自然に決まる初期値
- 単純な空状態の表示
- 明示済みのルールから導けるエラー表示
- 既存機能との一貫性を保つための軽微な挙動
- プロダクトの方向性を変えない低リスクな判断

### 勝手に決めてはいけないもの（未決事項として整理する）

- 機能を追加するかどうか
- データを永続化するか
- 削除時に確認を出すか
- 対応端末や対応環境
- 権限やユーザー区分
- 件数やサイズの上限
- 複数の妥当なユーザー体験が考えられるもの
- MVP の範囲を変える判断

## 既存コードがある場合

- 関係するコードとテストだけを確認し、現在の構成を把握してから設計する
- 既存の命名、設計パターン、ディレクトリ構成を尊重する。理想構成を押し付けない
- 変更内容は「追加・変更・削除」を区別して書く
- 仕様・設計・コード・テストの間に差異があれば明示する
- 関係のないリファクタリングを設計に含めない

## 文書管理方針

- design.md は 1 ファイルにまとめ、仕様設計と技術設計は章で分ける
- 記載内容の重複は「最重要原則 2: ファイル内の SSOT を守る」に従って排除する
- 変更履歴表は作らない。履歴は Git で管理する
- 更新時は必要な箇所だけ変更し、毎回文書全体を再生成しない
- 古くなった記述は残さず削除する
